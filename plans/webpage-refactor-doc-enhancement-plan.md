# `webpage` 重构文档深化方案

## 目标

围绕 `webpage/docs/重构计划` 现有 5 篇文档，补齐一套可直接支撑 V2 重构的文档体系，使其同时具备：

- 战略层：为什么重构、边界是什么、哪些问题先解决
- 架构层：状态流、模块边界、布局骨架、数据契约
- 执行层：分阶段迁移顺序、风险点、回退策略、验收标准
- 协作层：前后端接口对齐、测试要求、发布节奏、文档间引用关系

## 现有文档的主要问题

### 1. 优点

现有文档在方向上是对的，尤其已经覆盖了：

- 布局与容器层级
- 安全与 XSS 风险
- 测试体系建设
- UI/UX 体验升级
- 总体技术选型

### 2. 当前不足

但如果直接拿这些文档指导重构，会遇到几个问题：

1. 缺少与现有代码的一一映射
   - 文档提出了很多正确原则，但没有明确对应到哪些文件、哪些耦合点、哪些现状问题
   - 例如 `SearchPage`、`TopBar`、`AppSidebar`、`searchStore`、`apiClient` 都应该被明确标注为改造对象

2. 缺少迁移顺序
   - 还没有回答“先拆什么、后拆什么、哪些可以并行、哪些必须串行”
   - 这会导致重构时容易边改边乱

3. 缺少边界声明
   - 哪些是 V2 必做，哪些是增强项，哪些是延后项，目前不够清晰
   - 例如推荐流、命令面板、虚拟滚动、OpenAPI 类型生成，不一定都应该放在第一阶段完成

4. 缺少验收标准
   - 文档更多是建议，不够像规范
   - 需要补充“做到什么算完成”

5. 缺少风险与回退策略
   - 例如登录态、搜索 URL 化、无限滚动替换、图片链路、通知中心改造，这些都需要明确风险

## 建议新增的统一总纲结构

建议在 `webpage/docs/重构计划` 下新增一篇总纲文档，例如：

- `重构执行总纲.md`

这篇文档不替代原有文档，而是作为总索引，负责统一约束与目录导航。

### 总纲建议包含的章节

#### 1. 重构背景与范围

明确 V2 的重构范围：

- 包含：前端布局骨架、路由状态、搜索链路、设置系统、通知系统、预览系统、主题系统、测试基建、安全基线
- 不包含：后端搜索引擎重写、推荐算法真正上线、复杂商业化能力、完全重做视觉品牌

#### 2. 现状问题索引

把问题按模块挂到真实代码上：

- 页面层：`webpage/src/pages/SearchPage/index.tsx`
- 布局层：`webpage/src/components/layout/MainLayout.tsx`
- 顶栏与搜索：`webpage/src/components/layout/TopBar.tsx`
- 侧边栏：`webpage/src/components/layout/AppSidebar.tsx`
- 搜索状态：`webpage/src/features/search/store/searchStore.ts`
- API 客户端：`webpage/src/lib/api/client.ts`
- 认证守卫：`webpage/src/components/ProtectedRoute.tsx`
- 本地设置：`webpage/src/lib/settings.ts`

#### 3. V2 架构原则

建议明确写成硬规则：

- URL 是搜索条件的单一真实来源
- React Query 只管服务端状态
- Zustand 只保留客户端 UI 状态
- 页面组件只做编排，不做过重业务逻辑
- 所有浮层统一走 Overlay System
- 所有用户设置必须有 schema 校验与默认值回退

#### 4. 分阶段迁移路线

建议拆为 5 个阶段：

1. 地基期
   - 目录边界、Provider 整理、设计令牌、Overlay 规范、错误边界规范
2. 搜索核心期
   - URL 驱动搜索、参数解析、查询键重构、搜索页拆分
3. 布局与交互期
   - App-like Layout、Sidebar/TopBar 重组、移动端导航、预览层体系
4. 稳定性与安全期
   - Markdown 安全、图片链路、防 token 风险、埋点与错误监控
5. 测试与交付期
   - Vitest、MSW、关键路径测试、CI 约束

#### 5. 验收矩阵

按模块列出验收标准：

- 搜索：刷新不丢条件、可分享链接、浏览器前进后退正常
- 布局：主滚动域唯一、移动端无滚动穿透
- 状态：无服务端结果写入 Zustand
- 测试：核心工具与 store 有自动化覆盖
- 安全：Markdown 渲染链路无裸 `dangerouslySetInnerHTML`

#### 6. 风险与回退

例如：

- 搜索 URL 化可能影响历史逻辑
- 登录 hash token 提取逻辑改造可能影响 OAuth 回跳
- 图片加载重构可能造成缩略图请求激增
- 通知中心状态重构可能影响未读数一致性

## 一、`总体架构重构计划.md` 的增强方向

### 当前定位

它现在像一篇理念白皮书。

### 建议增强为

“架构总设计 + 分阶段执行蓝图”

### 应补充内容

1. 增加“现状与目标差距”章节
   - 明确 V1 当前真实问题，而不是只讲理想方案
   - 建议直接引用现有代码中的典型问题

2. 增加“模块边界图”
   - 页面层
   - feature 层
   - shared/lib 层
   - store 层
   - API 层

3. 增加“状态分类表”
   - URL 状态
   - React Query 状态
   - Zustand 状态
   - localStorage 设置
   - 临时 UI 状态

4. 增加“迁移顺序与依赖关系”
   - 哪些重构可并行
   - 哪些必须先完成再进行下一步

5. 增加“延期项列表”
   - 推荐流
   - 命令面板
   - OpenAPI 自动生成
   - 高级图片占位技术
   - 根据资源与收益决定是否进入首轮 V2

### 建议新增小节

- 现有代码问题映射
- V2 架构边界
- 阶段拆分与依赖关系
- 风险矩阵
- 验收矩阵

## 二、`UI层级和父子容器优化.md` 的增强方向

### 当前定位

它已经点中了很多核心问题，但目前偏“原则宣言”。

### 建议增强为

“布局系统重构规范 + 容器职责说明书”

### 应补充内容

1. 增加“目标布局树”
   - `AppShell`
   - `SidebarLayer`
   - `TopBarLayer`
   - `MainScrollArea`
   - `OverlayRoot`

2. 增加“现状映射”
   - `RootLayout`
   - `MainLayout`
   - `SearchPage`
   - `ResizableSidebar`
   - `TopBar`
   - `NotificationCenter`
   - `GlobalThreadPreview`
   - `FloatingBanner`

3. 明确“哪些组件必须 Portal 化”
   - 搜索建议面板
   - 通知中心
   - 预览层
   - Modal/Dialog
   - Tooltip/Dropdown

4. 明确“哪些地方禁止再做布局职责”
   - 页面组件里不再直接复制一套 Sidebar + Main 布局
   - 例如 `SearchPage` 当前实际上自己重复实现了一版主布局，这一点应该在文档中点出来

5. 增加“滚动域标准”
   - 页面唯一主滚动容器
   - 弹窗内部滚动容器
   - Sidebar 是否独立滚动
   - 移动端 bottom sheet 的滚动规则

6. 增加“z-index token 表”
   - 不只是描述层级，还要给出统一命名，例如 `--z-base`、`--z-sticky`、`--z-overlay`、`--z-modal`、`--z-toast`

### 建议新增小节

- 现状布局问题清单
- V2 标准布局树
- Portal 适用清单
- 滚动域与裁剪规则
- 分层与命名规范
- 布局验收清单

## 三、`安全升级.md` 的增强方向

### 当前定位

安全意识是对的，但还不够贴近项目当前代码。

### 建议增强为

“前端安全基线规范 + 当前风险清单”

### 应补充内容

1. 结合现有 Markdown 渲染链路
   - 项目里已经存在 `react-markdown`
   - 需要明确检查 `MarkdownText`、帖子预览、通知预览、关于页是否存在外链与 HTML 白名单问题

2. 增加“链接安全策略”
   - 站内链接
   - Discord 链接
   - 第三方下载站
   - 不可信域名跳转确认

3. 增加“认证安全迁移建议”
   - 当前 token 在 localStorage 中
   - V2 先做风险收敛，再评估是否迁移 HttpOnly Cookie
   - 文档里应把“短期方案 / 理想方案”分开

4. 增加“持久化状态校验”
   - 当前 `settings` 和部分 Zustand persist 缺少 schema 校验
   - 应明确使用 `zod` 或等价方式做恢复时校验

5. 增加“依赖安全与供应链”
   - 锁定依赖版本
   - 定期审计
   - 对第三方 UI 库、Markdown 插件、图片处理库建立准入原则

6. 增加“CSP 与部署安全”
   - 即使暂时不完全实施，也应列出目标策略
   - 至少定义 inline script、第三方图片域、connect-src 的边界

### 建议新增小节

- 当前代码的高风险入口
- Markdown 与外链安全基线
- Token 与本地持久化风险
- CSP 与部署策略
- 安全验收标准

## 四、`测试升级.md` 的增强方向

### 建议增强为

“测试策略 + 最小可行测试清单”

## 五、`细节打磨.md` 的增强方向

### 当前定位

这篇很有产品想象力，但有些内容已经接近“产品路线图”，需要从“重构必做项”里分离出来。

### 建议增强为

“体验规范 + 优先级分层文档”

### 应补充内容

1. 把内容分为三层优先级
   - P0：必须纳入 V2 首轮
   - P1：建议在 V2 稳定后补齐
   - P2：愿景项

2. 把“体验优化”和“产品创新”分开
   - 例如：搜索历史、零输入态、空状态优化，这些偏重构增强
   - 推荐流、趋势标签云、命令面板，更接近产品扩张

3. 增加“现有资产复用策略”
   - 看板娘图片资产
   - 现有 Banner 能力
   - 当前通知中心
   - 当前设置页

4. 增加“交互一致性规范”
   - 卡片 hover 行为
   - 列表/网格切换行为
   - Toast 触发规则
   - 错误 / 空 / 加载 / 成功 四态设计

5. 增加“移动端优先规则”
   - 首屏信息密度
   - 输入法遮挡
   - Bottom Tab 显隐
   - 单手可达区

### 建议新增小节

- 必做项与愿景项拆分
- 四态体验规范
- 移动端交互准则
- 看板娘与情感化交互边界
- 验收样例

## 额外建议新增的文档

除了增强现有 5 篇，我建议补两篇新文档，这样整个体系会完整很多。

### 1. `重构执行总纲.md`

作用：统一所有文档的导航、边界、阶段、验收与风险。

### 2. `现状问题清单与代码映射.md`

作用：把文档建议落到实际代码位置。

建议至少覆盖以下对象：

- `webpage/src/pages/SearchPage/index.tsx`
- `webpage/src/components/layout/TopBar.tsx`
- `webpage/src/components/layout/AppSidebar.tsx`
- `webpage/src/components/layout/MainLayout.tsx`
- `webpage/src/components/ProtectedRoute.tsx`
- `webpage/src/features/search/store/searchStore.ts`
- `webpage/src/lib/settings.ts`
- `webpage/src/lib/api/client.ts`
- `webpage/src/features/notifications/components/NotificationCenter.tsx`

这篇文档会非常实用，因为它能把“架构观点”转换成“具体拆哪里”。

## 我额外建议你在文档里明确写死的 10 条重构硬规则

1. 搜索条件必须 URL 化，不再以 store 为主源
2. 服务端结果不得写入 Zustand
3. 页面组件不得承担过重的数据转换逻辑
4. 所有浮层必须经过统一 Overlay System
5. 所有持久化设置都必须 schema 校验
6. 所有出站链接必须统一安全处理
7. 所有富文本渲染必须走安全白名单组件
8. 所有关键业务流程必须定义加载、空、错、成功四态
9. 所有新引入的复杂依赖必须先回答是否值得
10. 所有重构阶段都必须带测试与验收标准，而不是只改 UI

## 推荐的文档落地顺序

建议这样推进文档修订：

1. 先补 `重构执行总纲.md`
2. 再增强 `总体架构重构计划.md`
3. 再写 `现状问题清单与代码映射.md`
4. 然后增强 `UI层级和父子容器优化.md`
5. 再增强 `安全升级.md`
6. 再增强 `测试升级.md`
7. 最后整理 `细节打磨.md`

这样顺序最稳，因为先把总纲和边界立住，后面的文档就不会越写越散。

## 后续可直接落地的修订动作

下一步文档修订时，我建议输出成果至少包括：

- 一篇新的统一总纲
- 一篇新的现状问题映射文档
- 对现有 5 篇文档进行结构化改写
- 每篇文档都补上：
  - 目标
  - 现状问题
  - 方案
  - 风险
  - 验收标准
  - 与其他文档的关系

## 这轮方案的最终产出目标

完成后，`webpage/docs/重构计划` 应该从“灵感性方案集”升级为“可执行重构设计文档集”，能够直接指导后续进入 `code` 模式实施。
