## Webpage UI Optimization Plan

### Goal

Prioritize `webpage` frontend visual refinement around an Engram-inspired borderless fluid system, with token-first changes that improve the whole shell before touching isolated pages. Keep secondary UX fixes and small features documented, but do not let them derail the first implementation pass.

### What I learned

- The project already has the right foundation for token-driven theming: `webpage/src/shared/styles/globals.css`, `webpage/src/shared/styles/themes.ts`, `webpage/src/app/themes/ThemeProvider.tsx`, and `webpage/tailwind.config.js`.
- The internal style guide already points in the same direction as the requested redesign: fewer card stacks, stronger typography hierarchy, limited glass usage, unified shell surfaces, and no more than three visible layers.
- Engram’s useful references are not about copying exact visuals, but about structural behavior:
  - weak-card / fluid list treatment in `src/ui/components/display/ItemCard.tsx`
  - shell continuity between sidebar, header, and content in `src/ui/components/layout/MainLayout.tsx`, `Sidebar.tsx`, `Header.tsx`
  - typography via larger weight/size contrast rather than many boxed sections
  - fonts loaded as part of global theme setup in `src/ui/styles/GlobalStyles.tsx`
- Several current `webpage` screens still look boxy because token usage is inconsistent and many components directly mix backgrounds, borders, shadows, and hover treatments locally.

### Priority split

#### Phase 1 — Token and shell refactor first

This phase should be the main implementation target.

1. Consolidate visual tokens in `webpage/src/shared/styles/globals.css`
   - Introduce clearer semantic surface tokens for:
     - app background
     - shell/chrome layer
     - content layer
     - floating layer
     - input layer
     - subtle interactive hover/active states
   - Add missing typography tokens for more obvious hierarchy:
     - larger title scale
     - stronger section heading weight
     - calmer body/meta contrast
   - Add optional font tokens so themes can define CDN fonts without hardcoding them into all components.
   - Add a "text-only wallpaper mode" or equivalent token mode where wallpaper is visible with little or no global dim/overlay, while text remains readable through surface choices rather than a heavy page mask.

2. Improve Tailwind integration in `webpage/tailwind.config.js`
   - Map more of the `--od-*` semantic tokens into Tailwind color names so components stop repeating `bg-[var(--od-...)]` everywhere.
   - Add semantic utilities for typography, spacing, and surface states where repetition is high.
   - Keep this incremental; do not attempt a full Tailwind design-system rewrite in one pass.

3. Rebalance theme application in `webpage/src/app/themes/ThemeProvider.tsx`
   - Preserve the current wallpaper/glass algorithm, but tune it for a flatter Engram-like shell:
     - lighter content surfaces
     - smaller perceived depth gap between sidebar/topbar/content
     - stronger readability in text-only background mode
   - Ensure dropdowns, modals, preview panels, and notification layers remain sufficiently opaque even when glass/wallpaper is enabled.

4. Rebuild shell continuity
   - Update `webpage/src/widgets/layout/RootLayout.tsx`
   - Update `webpage/src/widgets/sidebar/ResizableSidebar.tsx`
   - Update `webpage/src/widgets/layout/AppSidebar.tsx`
   - Update `webpage/src/widgets/layout/TopBar.tsx`
   - Target outcome:
     - sidebar/topbar/content feel like one continuous composition
     - visible layering stays within three levels
     - fewer independent boxes with different backgrounds
     - stronger type-led sectioning instead of border-led sectioning

### Preference filtering implementation plan

This should be treated as a product/architecture feature, not just a UI setting.

#### Product semantics

- Preferences move from “saved search defaults” to “discovery filtering rules”.
- They affect:
  - `PlazaPage`
  - all-channel discovery / browse result surfaces
  - search suggestions
- They do not affect:
  - raw search-box typing
  - query token parsing itself
  - explicit user-entered manual search semantics
- The safest mental model is:
  - search box = intent input
  - preferences = discovery feed shaping
  - channel = explicit scope selector

#### Recommended model: single data-layer discovery filter, not front-end-only display hiding

Recommended choice: implement preferences as a reusable request-layer helper that augments discovery requests before they hit the API.

Why this is better than a pure display-layer filter:

- It keeps pagination, totals, banners, and suggestion counts consistent with what the user sees.
- It avoids fetching a lot of irrelevant content and then hiding it locally.
- It gives one place to define precedence rules instead of duplicating logic in Plaza, SearchPage, TopBar suggestions, and future discovery modules.
- It remains simpler than a full “dual-track” architecture because there is still only one result source per surface.

Why not pure dual-track (“data layer one set, display layer another set”):

- It creates confusing mismatch between total counts, suggestion hints, and rendered cards.
- It complicates infinite loading and cache keys.
- It makes later random-draw / recommendation modules harder to reason about.

#### Concrete architecture

1. Introduce a dedicated discovery-preferences mapper
   - New helper layer near search/preferences modules, e.g. a `buildDiscoverySearchParams(...)` utility.
   - Input:
     - current explicit surface context (`query`, `channel`, sort, tags, date range, etc.)
     - saved user preferences from `useUserPreferences`
     - a mode flag such as `discovery` vs `manual-search` vs `suggestion`
   - Output:
     - normalized `SearchUIRequest`
     - metadata describing whether preferences were applied and how

2. Split request semantics into three modes
   - `discovery-feed`
     - used by Plaza rails, all-channel browse, future recommendation modules
     - apply preferences by default
   - `suggestion`
     - used by `TopBar` / `SearchSuggestions`
     - apply preferences to candidate retrieval, but do not mutate the text input
   - `manual-search`
     - used by the main `/search` results once the user is intentionally searching
     - default should remain explicit query/channel driven, not silently filtered by preferences

3. Define precedence clearly
   - Recommended precedence order:
     - explicit manual query/tokens
     - explicit selected channel
     - saved discovery preferences
   - But for all-channel discovery surfaces where there is no explicit channel, preferences provide the default channel pool and include/exclude rules.
   - If the user explicitly enters a channel or search token, that should be treated as an intentional override, otherwise the behavior becomes hard to predict.

4. Use preferences differently by field type
   - `preferred_channels`
     - discovery mode: becomes default `channel_ids`
     - suggestion mode: narrows suggestion source pool
     - manual search mode: do not auto-inject if user already entered a channel or is performing a deliberate global search
   - `include_tags` / `exclude_tags`
     - discovery mode: merge into request filters
     - suggestion mode: use to bias/narrow returned suggestion candidates
     - manual search mode: should not silently rewrite query text
   - `include_keywords` / `exclude_keywords`
     - discovery mode: pass as backend filter fields only if the backend semantics are trustworthy
     - otherwise treat them as a later-phase enhancement, because keyword preference filtering can easily become too opaque to users
   - `sort_method`
     - discovery mode: becomes default sort only when the surface does not already define a stronger product sort
     - Plaza rail-specific sorts should usually remain product-owned and not be overridden by user preference sort

#### Surface-by-surface implementation

1. `webpage/src/features/plaza/api/plazaApi.ts`
   - Update rails to accept optional discovery filter input rather than hardcoding plain `searchApi.search(...)` calls.
   - Plaza should remain a product-composed page, so preferences should narrow the candidate pool, not replace each rail’s core sort meaning.
   - Example:
     - latest rail still sorts by `created_desc`
     - but candidate scope can be limited by preferred channels / excluded tags

2. `webpage/src/pages/SearchPage/index.tsx`
   - Split the current page semantics into:
     - all-channel browse / no-query exploration state
     - explicit search state
   - Recommended rule:
     - when query is empty and no explicit channel/filter is set, use discovery preferences
     - once the user types a real query or explicitly sets filters, do not silently force preferences into the request
   - This preserves “偏好进入筛选” for browse/discovery while protecting manual search intent.

3. `webpage/src/widgets/layout/TopBar.tsx`
   - Suggestion fetches should use the discovery-preferences helper in `suggestion` mode.
   - Do not inject preference tokens into `SearchTokenInput` value.
   - Suggestions can be preference-aware without making the input field look pre-filled or censored.

4. `webpage/src/features/search/api/searchApi.ts`
   - Keep raw `searchApi.search(...)` low-level and neutral.
   - Do not bury preference logic directly in this low-level function.
   - Add a thin higher-level request builder above it, so API utilities stay reusable and testable.

5. `webpage/src/features/preferences/lib/preferencesMapper.ts`
   - Keep current form mapping logic.
   - Add separate helpers for:
     - `toDiscoveryPreferenceContext(...)`
     - `mergeDiscoveryPreferencesIntoSearchRequest(...)`
   - Avoid reusing `applyPreferencesToSearchQuery(...)` as the main engine, because query-string rewriting is exactly what we want to avoid for this feature.

#### Cache and state implications

- React Query keys for discovery surfaces should include a stable preference signature.
- Suggested pattern:
  - derive a compact preference fingerprint from normalized preference values
  - include it in Plaza rail keys, suggestion keys, and browse-mode search keys
- This ensures preference changes refresh discovery content correctly without forcing unrelated manual-search caches to churn.

#### UX guidance

- Discovery surfaces should expose that preferences are active in a lightweight way.
  - Examples:
    - “已按你的偏好筛选” text near counts
    - a reset / temporarily ignore preference action on browse surfaces
- Do not mirror preference tags directly into the top search bar unless the user explicitly applies them as editable search conditions.
- Keep the distinction visible:
  - preferences shape what is shown
  - search box expresses what the user is asking for now

#### Recommendation summary

Best recommendation: use a single request-layer discovery filtering system with explicit surface modes.

- Not pure front-end hiding
- Not full dual-track data/display architecture
- Not query-string injection by default

This gives:

- predictable behavior
- consistent totals and pagination
- low duplication
- room to extend into Plaza recommendations later

#### Main open product decision

One rule still needs confirmation before implementation:

- when the user is on `/search` and explicitly selects a channel, should that explicit channel override preference channels, or should preferences still remain “higher than channel” and continue to constrain results inside a preferred subset?

Recommended default:

- explicit selected channel overrides preference channels
- preferences still apply only as soft discovery defaults when channel is not explicitly chosen

Reason:

- otherwise users will click a channel and still not understand why some content is missing, which feels like hidden censorship rather than preference shaping.

### Tag preference follow-up notes

- Current observed state during implementation review:
  - channel preferences are already the safer first-stage discovery filter
  - search suggestions are wired to preference-aware request shaping
  - `PlazaPage` has not yet been wired to preference filtering in the current implementation snapshot and should be treated as a separate rollout step
- Current production concern:
  - tag preferences can trigger backend instability / 502 on `/search`
  - because tag filters are passed as real backend `include_tags` / `exclude_tags`, they are not just presentation hints anymore
  - this makes tag preferences materially riskier than channel preferences

#### Recommended rollout strategy for tag preferences

Use a staged rollout instead of treating tag preferences exactly like channel preferences on day one.

1. Stage A — channel preferences stay authoritative for discovery narrowing
   - keep channel preference filtering active for:
     - empty search discovery
     - search suggestions
     - later Plaza integration
   - tag preferences should not yet be injected into backend discovery requests by default until the 502 failure mode is fully understood

2. Stage B — tag preferences become front-end-visible soft preferences first
   - show saved include/exclude tags in discovery UI as active preference chips / hints
   - allow users to explicitly apply them into the current advanced filter session with one action
   - do not silently inject them into every backend request yet

3. Stage C — only after validation, selectively promote tag preferences into request-layer filtering
   - if backend behavior is proven stable for real tag names across all indexed channels, then enable request-layer tag preference injection for discovery mode
   - keep explicit search still sovereign

#### Recommended UX model for tag preferences

Recommendation: do NOT fully sync preference tags into the advanced filter panel as if they are current explicit filters by default.

Why:

- it blurs the distinction between:
  - saved long-term preference
  - current one-off manual filter
- it risks making users think the search box / current session is already “edited” by the system
- it makes clearing current filters conceptually messy because users may not know whether they cleared session filters or saved preferences

Better model:

- advanced filter panel should show a dedicated lightweight block such as:
  - “发现偏好标签”
  - with include/exclude chips in a muted style
  - plus actions like:
    - “同步到标签筛选” / 一个开关
    - “暂时忽略偏好标签”
    - “去偏好页编辑”
- manual filter chips remain visually distinct from saved preference chips

#### Preferred interaction refinement

- Recommended concrete interaction:
  - add a toggle inside the advanced filter panel, near the tag section header
  - label suggestion: `同步偏好标签`
  - when off:
    - preference tags are only displayed as passive context
    - current manual tag filters remain independent
  - when on:
    - the panel's `标签筛选` section should visually and functionally merge in saved include/exclude preference tags
    - those merged tags should appear as pre-applied include/exclude states inside the tag list
    - user can still add more manual tag filters on top
  - when turned off again:
    - only the synchronized preference-derived tag states are removed from the active panel filter session
    - user-added manual tag states should remain untouched if possible

- Implementation note:
  - synchronized preference tags should be tracked separately from manual tag filters in local UI state, even if they render into the same `标签筛选` list
  - this preserves clean undo behavior and avoids “关掉开关把我自己点的标签也清掉了” confusion

#### Keyword preference recommendation

Saved preference keywords should be treated more cautiously than tags.

Reason:

- tags are structured filters with visible semantics
- keywords go straight into backend text search / FTS semantics and are much harder for users to predict
- silently injecting saved keywords into discovery requests or into the advanced filter panel can easily create “为什么搜不到 / 为什么结果这么怪” issues

Recommended model for keywords:

1. Do not auto-sync saved keywords into the live advanced filter session by default.
2. Show them in a separate passive block, e.g.:
   - `发现偏好关键词`
   - include keywords / exclude keywords
3. Provide a separate explicit toggle or action:
   - `同步偏好关键词`
   - or more conservatively `应用到本次搜索`
4. Keep this keyword sync independent from the tag sync toggle.

Why separate toggles are better:

- tag preference sync is relatively understandable
- keyword preference sync is much more intrusive and backend-sensitive
- users may want channel preference + tag preference, but not keyword preference

#### Recommended final behavior split

- channel preferences:
  - default-on for discovery surfaces
- tag preferences:
  - visible by default
  - can be merged into advanced filter tag state with a dedicated toggle
- keyword preferences:
  - visible by default
  - NOT auto-applied by default
  - only applied with a separate explicit toggle/action

#### UX wording suggestion

- `同步偏好标签` — affects only the panel tag filter state
- `同步偏好关键词` — affects only this search session, should likely show a subtle caution hint
- explanatory helper copy:
  - “偏好是长期展示倾向；开启同步后，会把它们临时并入本次高级筛选。”

#### Semantic split to preserve

- saved preference tags = long-term discovery bias
- advanced filter tags = current session constraints
- only when the user clicks “应用到本次筛选” should preference tags be copied into the live advanced filter state

### Random draw / card-pull feature notes

This feature now has a clearer product direction: it is not a separate search system, but a playful discovery action that draws from the already-allowed preference-scoped content pool. Anything outside user preferences should not enter the draw candidate pool at all.

#### Core semantics

- card draw = surprise discovery from the current allowed pool
- preference filtering remains upstream and authoritative
- explicit user scope can further narrow the pool before drawing
- the draw interaction should never silently expand beyond preference-safe content

Recommended precedence for candidate pool construction:

1. explicit temporary scope chosen for the draw session
2. saved discovery preferences
3. default discovery surface pool

That means:

- if the user picks a specific channel for draw, draw only inside that channel
- if the user does not pick a channel, draw from all preference-allowed channels
- excluded tags / blocked preference content should stay excluded

#### Recommended placement

Best recommendation: place the main random draw module on `PlazaPage`, not as a primary mode of `SearchPage`.

Additional comparison was discussed against a fully dedicated page, because a standalone route can also be a valid product shape depending on how theatrical and self-contained the feature should become.

Why Plaza is the better home:

- Plaza is already the product's discovery surface, so “抽卡 / surprise me” fits the page mental model naturally
- Search page is currently split between empty-state discovery and explicit search intent; adding a flashy draw mode there risks mixing “I am searching” with “surprise me” too aggressively
- Plaza has room for a visually distinct hero-level interactive block without polluting search semantics
- the draw result can feel like a special discovery ritual, while Search remains a tool-like page

Recommended SearchPage role:

- lightweight entry point only
- for example, a compact CTA in empty search state such as `去广场抽卡` or `来一抽` that routes into Plaza with draw UI open
- avoid turning `/search` into the main home of the feature

#### Plaza module vs dedicated page

Two viable homes now exist:

1. embedded module on `PlazaPage`
2. dedicated route such as `/draw` or `/gacha`

##### Option A — Plaza module

Pros:

- strongest semantic fit with existing discovery behavior
- lower implementation surface because it can reuse current Plaza preference-shaped content flow
- easier to keep the feature feeling like “one discovery tool among others” rather than a parallel product island
- simpler first rollout because entry, context, and fallback browsing already exist on the same page

Cons:

- visual impact is constrained by Plaza's existing information density
- the feature may feel less special if surrounded by banners, rails, and booklists
- scope selection and reveal states must coexist with other Plaza actions, which can dilute the ritual feeling
- future expansion into history / collection / themed draw events may start to feel cramped

Best when:

- first version should be fast, practical, and integrated with current discovery
- draw is a high-polish widget, not a separate product destination

##### Option B — Dedicated page

Pros:

- strongest stage for a theatrical, immersive reveal flow
- clearer mental model: user explicitly enters a “surprise me” mode instead of mixing it with normal browsing
- easier to support richer states later, such as:
  - draw history
  - saved favorite pulls
  - rotating themed pools
  - larger multi-draw reveal choreography
- easier to explain scoped drawing because the whole page can own controls like pool, channel, draw count, and result history

Cons:

- higher product and implementation cost because it becomes a new first-class route, not just a feature block
- more risk of feature isolation if users do not naturally discover or revisit the page
- requires an explicit navigation strategy from Plaza/Search/Sidebar instead of inheriting traffic from an existing discovery page
- can accidentally feel heavier than the actual utility if first version is still just “pick random thread from preference-safe pool”

Best when:

- the goal is a signature feature with strong identity and room to grow
- the desired tone is more ceremonial than utility-oriented

#### Current recommendation after comparison

Recommended default remains: start with a dedicated page only if the product goal is explicitly to make random draw a branded destination experience.

Otherwise, better first step is:

- ship as a prominent Plaza module now
- architect the draw UI as a self-contained component tree
- keep the option open to later lift the same module into a dedicated route with minimal redesign

In other words:

- if the priority is product clarity + fast integration -> Plaza module wins
- if the priority is coolness + ritual + future extensibility -> dedicated page wins

Given the latest wording from product discussion around “炫酷” and multi-draw presentation, a dedicated page is now a credible option and may actually be the better long-term home if we expect this feature to become a memorable signature surface rather than a side widget.

#### Hybrid recommendation

Best balanced approach:

1. create a dedicated route, e.g. `/draw`
2. use Plaza as the discovery and marketing entry point for it
3. place a strong CTA block on Plaza hero area:
   - `进入随机抽卡`
   - `按偏好来一抽`
4. keep SearchPage as a secondary lightweight entry only

Why this hybrid is attractive:

- Plaza remains the umbrella discovery surface
- dedicated page preserves the cool, focused experience
- channel scoping becomes much easier because the draw page can own its own control bar without fighting Plaza layout density
- future growth does not require tearing the module back out of Plaza later

#### Channel scoping if a dedicated page is chosen

Recommended draw-page scope controls:

- `按我的偏好抽` (default)
- `指定频道抽`
- optional later: `从当前频道来抽` when navigated with a channel context

Important rule:

- the selectable channel list should still be limited to preference-allowed channels in first pass
- no non-preference content should enter the candidate pool

This avoids the confusing question of “广场页怎么只抽某频道” entirely, because the channel scope belongs to the draw page toolbar rather than to Plaza's page-wide state.

#### Channel scoping on Plaza

Main open question raised by product discussion: how should Plaza handle “I only want to draw from one channel”?

Recommended answer:

- keep Plaza's page-level content rails preference-shaped as they are
- add a dedicated draw-scope control inside the draw module itself
- do not reuse the whole page's global rail state as the only draw scope selector

Recommended scope options inside the draw module:

1. `按我的偏好抽` (default)
   - uses all preference-allowed channels
2. `当前频道抽`
   - only shown if user entered Plaza from a channel context in the future
3. `指定频道抽`
   - opens a compact channel picker limited to preference-allowed channels
4. `忽略频道，只看偏好标签` is not recommended for first pass because it is harder to explain and depends more on backend tag stability

This keeps the interaction understandable:

- Plaza remains broad discovery
- draw module gets its own explicit scope
- user understands why a result came from a certain pool

#### Draw modes

Recommended first version:

- single draw (`1`)
- multi draw (`5` or `10`)

Why:

- easy to explain
- visually satisfying
- compatible with current card/list data without inventing rarity systems yet

Avoid in first pass:

- rarity simulation not backed by real content signals
- duplicate-protection rules across sessions
- long animation queues that block reading

#### Result presentation

Recommended result framing:

- one featured reveal card first
- if multi-draw, reveal as a staggered spread/grid after the lead card motion
- every result should immediately support:
  - preview
  - open thread
  - redraw
  - narrow future draws by same channel/tag when meaningful

The result area should feel more ceremonial than the normal thread grid, but still reuse thread preview/open actions so it stays product-consistent.

#### Data and architecture guidance

Recommended implementation model:

- build a dedicated front-end draw candidate request builder above existing search/plaza APIs
- source candidates from the same discovery request-layer preference helper used by Plaza/Search discovery
- then randomly sample on the front end from the returned candidate set for the current draw session

For first implementation, keep it simple:

- fetch a bounded candidate batch from already filtered discovery search
- sample randomly client-side
- if pool is too small, show that honestly instead of faking variety

This avoids introducing a backend-only draw endpoint in the first pass.

#### UX copy direction

Recommended labels:

- `随机抽卡`
- `来一抽`
- `十连发现`
- `从这些频道里抽` for scoped channel picker
- helper copy: `只会从你的偏好范围内随机发现内容`

#### Recommended phased rollout

1. Phase A — Plaza-only module
   - one featured draw block on Plaza hero/discovery area
   - default scope = all preference-allowed channels
   - supports 1-draw and multi-draw
2. Phase B — scoped draw
   - add in-module channel picker limited by preferences
   - allow “draw only from this channel” without changing whole Plaza page semantics
3. Phase C — lightweight Search entry
   - add CTA from empty search state into Plaza draw
   - avoid duplicating full draw UI on Search unless product later proves the need

3. Architecture optimization
   - Capture separately after UI pass.

### Validation checklist for implementation

- No major page visually exceeds three apparent layers.
- Sidebar, topbar, and main content read as one composition.
- Cards do not feel like nested boxes sitting on other boxes.
- Typography hierarchy is noticeably stronger even before color is considered.
- Banner becomes a clear hero area instead of a generic image card grid.
- Floating surfaces remain readable in wallpaper and glass modes.
- Dark and light themes both remain usable.
- Mobile shell still works: sidebar drawer, topbar, bottom tab bar, and content spacing remain intact.
- Search input no longer double-submits or misbehaves during Chinese IME composition.

### Out of scope for first pass

- Full preference filtering productization
- Full Plaza random draw feature
- Large search architecture rewrite
- Broad non-UI refactors unrelated to touched files

### Execution note

When implementation starts, favor token/surface changes that produce broad visual improvement across the app before polishing individual pages. If a page still feels overly boxed after token cleanup, then perform page-local restructuring rather than adding more one-off styles.
