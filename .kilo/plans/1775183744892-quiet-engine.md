# 书单 Page 设计与实施计划（前端）

## 目标与范围

把索引页的书单能力做成**全操作页面**（不只是浏览）：

1. 书单列表浏览（公开/我的/我收藏）
2. 书单创建、编辑、删除
3. 书单详情与书单内帖子管理（增删、备注、排序）
4. 与现有帖子预览、搜索、收藏体系打通

不在本期实现的能力（后续迭代）：

- 拖拽排序（先用数字排序权重编辑）
- 批量跨页操作
- 书单协作/共享权限细分

---

## 后端与 API 现状（已确认）

### 已有路由

- `POST /v1/booklist/save` 创建书单（query 传参）
- `GET /v1/booklist/list/page` 公开书单分页
- `GET /v1/booklist/my/list/page` 我的书单分页（支持 created/collected 过滤）
- `GET /v1/booklist/detail/{booklist_id}` 书单详情
- `PUT /v1/booklist/update/{booklist_id}` 更新书单
- `DELETE /v1/booklist/delete/{booklist_id}` 删除书单
- `POST /v1/booklist/item/add/{booklist_id}` 批量加帖子
- `DELETE /v1/booklist/item/delete/{booklist_id}` 批量删帖子
- `GET /v1/booklist/item/list/page/{booklist_id}` 书单内帖子分页
- `PATCH /v1/booklist/item/update/{booklist_id}/{thread_id}` 更新书单项（备注、排序）
- 收藏通用接口：
  - `POST /v1/collection/batch/add?target_type=2`
  - `POST /v1/collection/batch/remove?target_type=2`

### 关键数据模型（前端可用）

- `BooklistDetail`：含 `collected_flag / item_count / collection_count / view_count / is_public / display_type`
- `BooklistItemDetail`：含帖子核心字段 + `comment / display_order / added_at / collected_flag`

### 技术注意点

- `create/update` 目前是 **query 参数**（不是 JSON body）。
- `list_*` 的 `offset` 在后端按 `offset * limit` 处理，语义更像“页号”而非“行偏移”；前端分页要专门兼容。

- 删除帖子：单条删除 +（后续）批量选择删除
- 编辑条目：inline 编辑 `comment` 与 `display_order`

## 数据流与状态策略

- 使用 TanStack Query 管理书单与条目数据
- 推荐 query key：
  - `['booklists', scope, filters]`
  - `['booklist-detail', id]`
  - `['booklist-items', id, page, pageSize]`
- 变更后精确失效：
  - 创建/删除书单：失效列表
  - 更新书单：失效详情 + 列表
  - 条目增删改：失效条目列表 + 详情统计
- 乐观更新仅用于“收藏/取消收藏”按钮；其余先走保守刷新

---

## API 映射细则（前端实现约束）

1. 创建/更新书单接口走 query 参数，`axios.post(url, null, { params })` / `put(..., null, { params })`
2. 分页参数统一封装为 `{ pageIndex, pageSize } -> { offset: pageIndex, limit: pageSize }`
3. 收藏书单：调用 collection batch 接口，body 为 `number[]`，query `target_type=2`
4. 添加帖子时，`thread_id` 需 number；现有 thread_id 多为 string，要做显式转换与校验

---

## UI/UX 重点规范

1. 书单卡片与现有主题变量保持一致（`--od-*`），不引入新视觉体系
2. 书单详情中的帖子展示尽量复用现有线程组件，避免双套样式维护
3. 管理操作（删除书单、删除条目）必须二次确认
4. 对权限失败（403）做明确提示：
   - “该书单仅创建者可修改”

## 风险与规避

1. **分页语义歧义**：后端 offset 实际为页号，前端统一适配层封装，避免全局误用。
2. **接口风格不一致**：create/update 用 query，容易误传 body；API 层统一封装避免页面直接调用。
3. **ID 类型不一致**：thread_id 在不同模型里 string/number 混用；统一 helper 做 parse + 防御。
4. **权限失败体验**：私有书单/非 owner 操作可能频繁 403；页面级错误文案要明确。

# 广场 Page 调研与方案（推荐卡 + 书单 + Banner）

## 调研结论（后端与前端现状）

1. 当前没有独立“广场推荐聚合”API，现有能力可组合：
   - 帖子推荐池：`POST /v1/search/`
   - Banner：`GET /v1/banner/active`
   - 书单：`GET /v1/booklist/list/page`
2. 搜索接口支持的排序能力足够做经典广场分区：
   - `comprehensive`（综合推荐）
   - `created_at`（最新上新）
   - `reaction_count`（点赞热度）
   - `reply_count`（讨论热度）
   - 时间窗可用 `created_after/active_after` 做“近期热度”约束
3. Banner 系统有完整申请链路，前端已接入申请：
   - `POST /v1/banner/apply`
   - `GET /v1/banner/active`
4. 搜索响应本身也携带 `banner_carousel`，可作为“频道上下文 Banner”来源；广场页建议优先用 `banner/active`，搜索页继续使用 `banner_carousel`。

## 产品定位

广场页是“发现入口”，聚焦内容推荐与分发，不承担重搜索表达式编辑：

- Banner：运营曝光与活动入口
- 推荐卡流：按策略切片的帖子集合
- 书单精选：可订阅、可进入深读

## 信息架构（页面模块）

### 1) Hero Banner 区

- 数据源：`/v1/banner/active`
- 展示：轮播 + 主题文案 + 跳转帖子预览
- CTA：
  - 「查看帖子」
  - 「申请 Banner」(复用现有 `BannerApplicationModal`)

### 2) 推荐卡分区（核心）

一期建议 4 条推荐轨道：

1. 最近上新
   - `sort_method=created_at&sort_order=desc`
2. 点赞数飙升（近7天）
   - `sort_method=reaction_count&sort_order=desc&created_after=-7d`
3. 讨论升温（近7天）
   - `sort_method=reply_count&sort_order=desc&active_after=-7d`
4. 今日精选（综合）
   - `sort_method=comprehensive&sort_order=desc`

每条轨道形态：

- 顶部标题 + 副标题 + “查看更多”（跳搜索页并带参数）
- 卡片内容复用 `ThreadCard` / `ThreadListItem` + 统一 `ThreadPreviewOverlay`

### 3) 书单精选区

- 数据源：`/v1/booklist/list/page`
- 默认排序：`sort_method=3`（收藏数）或 `sort_method=5`（更新时间）
- 展示：横向卡片流（复用 `BooklistCard` 的视觉）
- CTA：
  - 「进入书单页」
  - 「创建书单」

## 路由与导航策略

推荐两种可选路径：

- 方案 A（推荐）：`/` 作为广场页，搜索改为 `/search`
  - 优点：符合“首页即发现”心智
  - 影响：需同步 `TopBar`、`MobileTabBar`、搜索 query 路由逻辑
- 方案 B（低风险）：新增 `/plaza`，保持 `/` 仍为搜索
  - 优点：迁移成本低
  - 缺点：入口分散，首页价值弱

## 前端实现设计（复用与主题）

### 新增模块

- `src/pages/PlazaPage/index.tsx`
- `src/features/plaza/api/plazaApi.ts`
- `src/features/plaza/components/`
  - `PlazaBannerSection`
  - `PlazaThreadRail`
  - `PlazaBooklistSection`

### 强制复用（避免重复造轮子）

1. 帖子卡片：`ThreadCard` / `ThreadListItem`
2. 帖子详情：`ThreadPreviewOverlay`
3. 书单卡片：`BooklistCard`
4. Banner申请：`BannerApplicationModal`
5. 全部色彩/边框/背景使用 `--od-*` 变量

### 数据与缓存

- Query Keys：
  - `['plaza', 'banners']`
  - `['plaza', 'threads', railKey]`
  - `['plaza', 'booklists', sort]`
- TTL：
  - Banner 60s
  - 推荐轨道 60~120s
  - 书单精选 120s

## 算法策略（一期可执行）

由于暂无独立推荐服务，一期采用“规则推荐 + 多轨道曝光”：

1. 分轨取数，避免单一排序霸榜
2. 轨道内去重，跨轨轻量去重（同一 thread 最多出现在 2 个轨道）
3. 使用时间窗抑制历史高赞长期占位（`created_after/active_after`）
4. 保留 `comprehensive` 作为探索槽位

后续可迭代：

- 引入点击/预览/收藏行为特征
- 用户画像分层（新用户/回访）
- 服务端聚合接口（一次返回多轨道）

## 交互与可用性细节

1. 首屏优先展示 Banner + 一条推荐轨道，后续轨道懒加载
2. 每个分区失败不拖垮全页（局部错误态）
3. 对“无结果轨道”自动隐藏并补位
4. 移动端轨道改横滑卡片，保持主题与间距体系一致

## 分阶段落地

### Phase P1（1~2 天）

- 新增 `/plaza` 页面
- 上线 Banner + 3 条推荐轨道 + 书单精选
- 打通帖子预览与 Banner申请弹窗

### Phase P2（2~3 天）

- “查看更多”跳搜索并自动注入参数
- 轨道去重与降噪策略
- 空态/错误态细化

### Phase P3（后续）

- 首页路由切换评估（`/` -> 广场）
- 服务端聚合推荐接口（减少前端并发请求）
- AB 实验（轨道权重和排序）

## 风险与规避

1. 多轨道并发请求多：用 React Query 缓存 + 懒加载首屏外轨道。
2. 推荐“飙升”定义不精确：一期先时间窗近似，后续补增量指标。
3. 路由迁移冲击：先上 `/plaza` 验证数据与体验，再决定是否切首页。

## 验收标准

1. 用户可在广场看到 Banner、推荐轨道、书单精选三大模块。
2. 推荐卡点击可打开统一帖子预览浮层。
3. Banner 区可直接触发申请流程。
4. 书单卡可跳转到书单详情。
5. 页面在桌面/移动端样式一致、主题变量一致、无视觉割裂。

# Preferences + 图片自愈策略（前端）

## 背景与目标

当前两个 API 已在 OpenAPI 暴露，但前端价值没有被完整发挥：

1. `/v1/fetch-images/`：已存在 `fetchImagesApi` 封装，但未接入实际 UI 链路。
2. `/v1/preferences/users/{user_id}`：后端已支持读写用户搜索偏好，但前端尚未消费。

本期目标（仅前端）：

1. 把图片 404/失效修复做成“无感自动恢复”。
2. 把用户偏好接入首次引导与“我的”入口，形成可编辑闭环。
3. 保持现有主题体系与组件复用，不改后端逻辑。

## 现状确认

1. `fetchImagesApi.refresh(items)` 存在，但 `webpage/src` 内无调用方。
2. 图片展示点分散：
   - `ThreadCard` 直接 `<img>`
   - `ThreadListItem` 使用 `LazyImage`
   - 通知中心、广场 Banner、书单卡也有直接 `<img>`
3. 首次引导当前由 `SearchPage` 中 `od_onboarding_shown` 本地开关控制。
4. 移动端已存在底部 `我的` tab（目前跳 `/settings`），桌面侧栏底部头像仅展示+登出。
5. 偏好接口参数需要 `user_id`（path）与可选 `guild_id`（query），鉴权已由 cookie/token 完成。

## 总体方案

### A. 图片自愈：建立“失败上报 -> 批量刷新 -> 局部回填”链路

设计原则：

1. 不阻塞当前渲染，先显示占位，后台自愈。
2. 去重、限频、批量，避免请求风暴。
3. 优先修复线程缩略图（thread thumbnail），后续再扩展书单/Banner。

关键机制：

1. 在图片组件层捕获 `onError`，上报 `{ thread_id, channel_id? }`。
2. 统一进入 `thumbnailRepairQueue`（内存队列）：
   - 去重：同一 `thread_id` 短时间只入队一次
   - 节流：如 800ms 聚合窗口
   - 批量：一次最多 N 条（如 20）
3. 调用 `/v1/fetch-images/` 返回最新 `thumbnail_urls`。
4. 成功后写入前端短期缓存，并触发相关 Query 局部更新（`setQueryData`）或失效刷新。
5. 失败容错：
   - 429/5xx 退避重试（指数退避上限）
   - 连续失败熔断一段时间，防止循环打点

### B. 偏好系统：首次引导 + “我的”页面编辑

设计原则：

1. 偏好是“账号级+可跨端”的，优先后端保存，本地只做临时 UI 状态。
2. 首次引导不只展示说明，直接可落地偏好（频道、排序、图片模式等）。
3. 桌面和移动端统一入口语义：都进入“我的”页面。

关键机制：

1. 新建前端 `preferencesApi`：封装 `getByUserId/updateByUserId`。
2. 新建 `useUserPreferences`（React Query）：
   - 拉取策略：登录成功后按需拉取
   - 404 视为“未设置”，走默认偏好并允许首次提交
3. 首次引导联动：
   - 保留 `od_onboarding_shown` 作为“UI引导是否展示”标记
   - 引导完成时可选择“写入偏好到服务器”
4. 新建 `/me` 页面：
   - 基础资料区：头像、昵称、ID（只读）
   - 偏好区：偏好频道、默认排序、每页数量、预览图片模式、关键词黑白名单
   - 保存按钮：提交 `PUT /preferences/users/{user_id}`
5. 入口改造：
   - 侧栏底部头像块新增“我的”可点击入口（或整体可点）
   - 移动端底部 tab 的“我的”从 `/settings` 切换到 `/me`

# 个人主页系统重构（讨论版 v0.1）

## 方向结论（与你的想法一致）

把“我的”从单一偏好快捷页升级为统一的个人中心系统：

1. **个人中心（管理向）**：集中管理我的书单/收藏/关注/偏好/我的帖子。
2. **个人展示页（对外向）**：展示用户公开信息、精选书单、热门帖子。
3. **实体层归位**：在 `src/entities` 建立 `user` 领域的统一模型与 UI 组件。

这比“侧栏底部一个按钮”更合理，也更可扩展。

## 目标信息架构

### A. 我的中心（`/me`，登录态）

建议顶部个人卡 + 二级导航 Tab：

1. `概览`：统计卡（书单数/关注数/收藏数/帖子数）+ 最近动态

3. `我的收藏`：帖子收藏列表（可复用现有搜索卡片流）

5. `我的帖子`：按作者过滤的帖子列表
6. `偏好设置`：当前 preferences 表单（已完成部分迁移）
