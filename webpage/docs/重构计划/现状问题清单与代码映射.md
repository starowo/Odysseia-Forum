# Odysseia 前端现状问题清单与代码映射

## 1. 这篇文档的作用

这篇文档只回答一个问题：

**V2 重构到底要改哪些真实代码。**

它不讲大原则，只做问题定位。

---

## 2. 页面层问题

## [`SearchPage`](../../src/pages/SearchPage/index.tsx:40)

### 当前问题

- 单文件体量过大
- 同时承担布局、搜索输入、筛选、分页、banner、帖子合并、预览、引导弹层等职责
- 自己重复实现了一套侧边栏加主内容布局
- 和 [`TopBar`](../../src/components/layout/TopBar.tsx:36)、[`AppSidebar`](../../src/components/layout/AppSidebar.tsx:14)、[`useSearchStore`](../../src/features/search/store/searchStore.ts:65) 耦合过深

### 重构方向

- 拆成页面容器加多个 feature section
- 搜索条件改为 URL 驱动
- 搜索结果改为 query hook 驱动
- 布局回收给统一 App Shell
- banner 和预览状态从页面主体逻辑中解耦

---

## [`FollowsPage`](../../src/pages/FollowsPage/index.tsx:16)

### 当前问题

- 仍然依赖全局 `selectedChannel` 作为筛选来源
- 页面筛选条件和搜索页存在隐式共享
- 频道数据再次请求

### 重构方向

- 明确“关注页是否继承全局频道上下文”
- 页面条件要么 URL 化，要么在页面内自洽
- 抽统一 `channels` 查询 hook

---

## [`SettingsPage`](../../src/pages/SettingsPage/index.tsx:25)

### 当前问题

- 逻辑主要可用，但配置项直接和本地存储结构绑定
- 缺少 schema 校验
- 页面本身过长，设置分组虽清楚但还不算模块化

### 重构方向

- 设置 schema 独立
- 存储恢复时先校验再合并默认值
- 按主题、布局、通知、实验项拆子模块

---

## 3. 布局层问题

## [`MainLayout`](../../src/components/layout/MainLayout.tsx:14)

### 当前问题

- 负责侧边栏、顶栏、主区域，但没有真正成为全站唯一布局骨架
- 搜索页绕开了它，说明布局抽象不完整

### 重构方向

- 升级为统一 App Shell
- 规定顶部栏、侧边栏、主滚动区职责
- 页面不再自行复制主布局

---

## [`RootLayout`](../../src/components/layout/RootLayout.tsx:5)

### 当前问题

- 目前只是简单包一层 `Outlet`
- 没有承担 overlay root、全局层级管理、全局滚动规范等职责

### 重构方向

- 作为最外层应用壳根节点
- 统一挂全局 overlay 容器、看板娘、回顶、预览层等全局能力

---

## [`TopBar`](../../src/components/layout/TopBar.tsx:36)

### 当前问题

- 组件承担搜索框、高级筛选、建议下拉、标签筛选等多个层级职责
- 未来继续扩展会越来越重
- 下拉和浮层逻辑仍偏内嵌

### 重构方向

- 拆成搜索输入区、快速操作区、高级筛选区
- 搜索建议和浮层进入统一 overlay 策略
- 筛选项只负责展示和派发，不直接承担复杂状态策略

---

## [`AppSidebar`](../../src/components/layout/AppSidebar.tsx:14)

### 当前问题

- 同时承担频道切换、导航、通知入口、主题切换、用户信息、登出
- 功能太多，未来难以维护
- 频道列表查询逻辑与别处重复

### 重构方向

- 拆成导航区、频道区、用户区、通知入口区
- 提供统一频道数据来源
- 把用户动作和展示解耦

---

## [`ResizableSidebar`](../../src/components/ResizableSidebar.tsx:1)

### 当前问题

- 当前仍属于布局组件内部能力
- 是否保留“可拖拽宽度”需要重新评估

### 重构方向

- 明确它是桌面增强项，不应影响整体布局结构
- 如果保留，应降为 App Shell 的一个可选能力

---

## 4. 状态管理问题

## [`useSearchStore`](../../src/features/search/store/searchStore.ts:65)

### 当前问题

- 混合了搜索条件、分页、banner、帖子预览、浮层相关状态
- 部分状态本应属于 URL
- 部分状态本应属于局部 UI
- `persist` 只做了部分处理，边界不清晰

### 重构方向

- 拆分为 URL 状态、服务端状态、本地 UI 状态
- store 只保留必要的客户端 UI 状态
- 预览状态和搜索状态考虑拆开

---

## [`useSettings`](../../src/hooks/useSettings.ts:4)

### 当前问题

- 本质上是 localStorage 包装器加事件广播
- 不是问题很大，但缺少类型校验与更强的状态边界

### 重构方向

- 评估迁移到独立 settings store
- 保留轻量实现也可以，但要补 schema 校验和版本兼容策略

---

## [`lib/settings.ts`](../../src/lib/settings.ts:3)

### 当前问题

- 有默认值体系，但对污染数据缺少严格校验
- 主题兼容处理是手写的，后续扩展会变乱

### 重构方向

- 引入 schema
- 加版本字段和迁移逻辑
- 设置项按模块拆分定义

---

## 5. 数据请求与协议层问题

## [`apiClient`](../../src/lib/api/client.ts:12)

### 当前问题

- 已有统一入口，这是优点
- 但认证错误处理、日志、重试、错误分类还比较轻
- token 仍存在 localStorage 风险

### 重构方向

- 明确请求层错误分类
- 区分认证失效、权限不足、网络失败、服务异常
- 作为全局副作用入口之一，例如错误事件分发

---

## [`searchApi`](../../src/features/search/api/searchApi.ts:32)

### 当前问题

- 已有参数映射层，这是正确的
- 但页面侧仍然承担了不少参数拼装和状态解释职责

### 重构方向

- 把 URL 参数到请求参数的转换再前置一层
- 页面不直接知道后端协议细节

---

## [`authApi`](../../src/features/auth/api/authApi.ts:17)

### 当前问题

- 认证检查和退出逻辑比较简单
- 和当前 token 存储方案强绑定

### 重构方向

- 保持 API 层简单
- 认证状态与重定向策略应上移到专门的 auth flow 层

---

## [`followsApi`](../../src/features/follows/api/followsApi.ts:23)

### 当前问题

- 结构清晰
- 但关注未读、通知中心、关注页之间存在语义交叉

### 重构方向

- 明确未读数的唯一来源
- 定义通知与关注的边界

---

## 6. 鉴权与路由问题

## [`ProtectedRoute`](../../src/components/ProtectedRoute.tsx:6)

### 当前问题

- 承担了 token hash 处理、加载态、重定向等多项职责
- 和 [`App`](../../src/app/App.tsx:34) 存在 token 提取逻辑重复

### 重构方向

- 统一 token 回收入口
- `ProtectedRoute` 只负责路由守卫
- 登录回跳逻辑单独收敛

---

## [`router`](../../src/app/router.tsx:47)

### 当前问题

- 路由结构基本清楚
- 但还没有真正体现 URL 驱动搜索的架构价值

### 重构方向

- 明确每个页面有哪些 URL 状态
- 搜索页优先完成查询参数标准化

---

## 7. 浮层与全局交互问题

## [`NotificationCenter`](../../src/features/notifications/components/NotificationCenter.tsx:27)

### 当前问题

- 同时承担静态通知、关注更新、关闭逻辑、预览触发
- 是一个典型的“功能可用但职责过多”的组件

### 重构方向

- 通知数据组装和通知面板 UI 分离
- 进入统一 overlay 体系
- 明确未读数、关闭态、跳转行为的优先级

---

## [`GlobalThreadPreview`](../../src/app/App.tsx:64)

### 当前问题

- 全局预览方向是对的
- 但预览状态现在散落在搜索 store 语义里，不够干净

### 重构方向

- 预览改为独立 preview flow
- 统一入口，页面只发打开事件

---

## [`FloatingBanner`](../../src/app/App.tsx:63)

### 当前问题

- 与搜索页 banner 可见性和 store 状态有关联
- 语义上属于全局展示层，但触发来源在搜索页内部

### 重构方向

- 分离“页面 banner”和“全局浮动 banner”职责
- 降低对搜索页内部状态的耦合

---

## 8. 工具与展示层问题

## [`MarkdownText`](../../src/components/common/MarkdownText.tsx:1)

### 当前问题

- 这是安全与展示的重要入口
- 需要作为 V2 安全审查重点对象

### 重构方向

- 明确允许的 Markdown 范围
- 统一外链处理
- 禁止危险 HTML 注入链路

---

## [`LazyImage`](../../src/components/common/LazyImage.tsx:1)

### 当前问题

- 图片加载体验和失败回退是资源类站点核心能力
- 需要和图片抓取链路一起评估

### 重构方向

- 补重试、降级、失败占位策略
- 明确是否需要预加载与并发控制
