# Odysseia 前端 V2 总体架构重构计划

## 1. 文档目的

这篇文档不是口号，也不是愿景摘要。

它负责回答 5 个实施问题：

- 这次重构到底要解决什么
- 当前系统的关键失衡点在哪里
- V2 的目标架构长什么样
- 实施要按什么阶段推进
- 每个阶段做完以后，怎么判断它真的完成了

如果后续进入实现，这篇文档应该能直接作为重构路线图使用。

---

## 2. 重构背景

当前前端已经具备完整产品雏形：

- 有登录链路
- 有搜索主链路
- 有关注、通知、设置、主题、看板娘、帖子预览等功能
- 技术栈本身并不落后，已经使用了 [`React Query`](../../src/app/App.tsx:2)、[`Zustand`](../../src/features/search/store/searchStore.ts:1)、[`React Router`](../../src/app/router.tsx:1)、[`Tailwind`](../../src/styles/globals.css:1)

问题不在于“能力缺失”，而在于：

**V1 在快速迭代中把很多正确的能力堆出来了，但这些能力之间的边界没有同步长出来。**

结果就是：

- 代码能跑，但页面越来越重
- 状态能用，但边界越来越模糊
- 布局能看，但主壳层并不统一
- 文档有方向，但实施细度不足

V2 的任务不是推翻重写，而是把这些已有能力重新编排成一个可扩展系统。

---

## 3. 当前架构的核心问题

这里不泛泛而谈，只点对后续实施最关键的问题。

### 3.1 页面巨石化

最典型的是 [`SearchPage`](../../src/pages/SearchPage/index.tsx:40)。

它同时承担了：

- 页面布局
- 搜索输入状态
- URL 同步的一部分
- 搜索条件解析
- 查询请求触发
- banner 展示与联动
- 分页与无限加载
- 预览打开
- onboarding 浮层
- 与看板娘的联动

这意味着：

1. 搜索页很难独立重构一部分而不影响其他部分
2. 页面职责已经明显超过“页面容器”范围
3. 后续任何目录优化、状态优化、布局优化，最终都会卡在这个文件上

### 3.2 状态边界失衡

当前 [`useSearchStore`](../../src/features/search/store/searchStore.ts:65) 是第二个核心症结。

它同时承载：

- 搜索条件
- 分页
- 标签筛选
- banner 状态
- 预览状态
- 一部分全局 UI 语义

问题不是“用了 Zustand”，而是**把不该放一起的状态放到了一起**。

直接后果：

- 本该 URL 化的状态没有完全 URL 化
- 本该由 React Query 管的结果周边状态，被页面和 store 共同组织
- 本该独立的预览流，被绑在搜索语义里

### 3.3 布局骨架不是真正统一的

现在已经有 [`RootLayout`](../../src/components/layout/RootLayout.tsx:5) 和 [`MainLayout`](../../src/components/layout/MainLayout.tsx:14)，但真正最重要的页面 [`SearchPage`](../../src/pages/SearchPage/index.tsx:453) 仍然自己复制了一套 Sidebar + Main 结构。

这说明当前“有布局组件”，但“没有应用骨架”。

直接问题：

- 页面行为不一致
- 布局调整无法全局收口
- 滚动域、层级、移动端行为难以统一

### 3.4 全局能力挂载点分散

当前全局能力散落在多个层级：

- [`FloatingBanner`](../../src/app/App.tsx:63)
- [`GlobalThreadPreview`](../../src/app/App.tsx:64)
- [`NotificationCenter`](../../src/features/notifications/components/NotificationCenter.tsx:27)
- [`MascotBar`](../../src/components/layout/RootLayout.tsx:9)
- 各类搜索建议、高级筛选面板

问题在于这些能力有的是页面级，有的是全局级，有的是局部浮层，但现在没有一套统一的挂载和分层规则。

### 3.5 目录架构的分层已经开始不够用

当前目录已经有 feature-based 的雏形，但还不够彻底。

例如：

- [`components`](../../src/components) 同时承载基础 UI、布局组件、页面块级组件
- [`pages`](../../src/pages) 里有页面容器，也有大量业务逻辑
- [`lib`](../../src/lib) 和 feature 内部工具同时存在，但边界不够稳定
- 某些全局能力挂在 [`app`](../../src/app) 或某个 feature 里都说得通，但没有统一口径

这会导致随着重构推进，目录越来越像“按历史堆出来”的结果，而不是按职责自然分层。

## 4. V2 要达成的总体目标

V2 不追求一步做到完美，而追求把架构拉回可维护状态。

### 4.1 页面层目标

页面组件只负责：

- 读取路由状态
- 组合 widgets 和 features
- 渲染页面结构

页面组件不再负责：

- 大量协议转换
- 混合型状态协调
- 直接管理多个全局副作用

### 4.2 状态层目标

建立明确的四类状态边界：

1. URL 状态
2. React Query 服务端状态
3. 客户端 UI 状态
4. 本地持久化设置状态

状态原则详见 [`状态管理与数据流重构.md`](./状态管理与数据流重构.md)。

### 4.3 布局层目标

建立真正的 App Shell：

- 主骨架统一
- 主滚动区唯一
- 页面不自建主布局
- 浮层进入统一 overlay 体系

布局原则详见 [`UI层级和父子容器优化.md`](./UI层级和父子容器优化.md)。

### 4.4 目录层目标 [x]

让目录和职责对齐，而不是继续用目录掩盖职责混乱。

方向详见 [`目录架构升级建议.md`](./目录架构升级建议.md)。

### 4.5 工程层目标

让重构可以持续落地，而不是写一轮文档后重新失控：

- 改动有顺序
- 阶段有验收
- 测试能跟上
- 风险可控

## 5. V2 目标架构

这一部分给出目标状态，不要求一步到位，但后续改造要朝这个方向收敛。

## 5.1 分层结构

推荐分成以下几层：

### `app`

负责应用装配层。

包括：

- provider 组合
- router
- app shell
- 全局挂载层

### `pages`

负责路由页面容器。

要求：

- 不写过重业务逻辑
- 不直接承载复杂状态流
- 只组合 widgets 和 features

### `widgets`

负责页面块级复用模块。

例如：

- 顶栏
- 侧边栏
- 通知面板
- 帖子预览壳层

### `features`

负责业务能力模块。

例如：

- search
- threads
- follows
- auth
- notifications
- banner
- mascot
- settings

建议每个 feature 逐步收敛出：

- `api`
- `components`
- `hooks`
- `lib`
- `model`

### `shared`

负责真正跨业务复用的能力。

例如：

- 基础 UI
- hooks
- api client
- 工具函数
- config
- types

### `entities` 可选预留

如果后续重构顺利，可以补 `thread`、`channel`、`user` 等实体层，承接领域级类型和小型展示片段。

---

## 5.2 数据流目标

搜索主链路统一成：

`URL -> 参数解析 -> Query Hook -> 页面渲染`

而不是继续使用：

`Input -> Store -> 多个 useEffect -> API -> 页面再拼状态`

认证主链路统一成：

`token 回收入口统一 -> auth query -> route guard 只做放行判断`

预览主链路统一成：

`页面或组件发起 preview action -> 独立 preview store 或 flow -> 全局预览层渲染`

---

## 5.3 应用骨架目标

目标布局树应收敛成：

```text
AppRoot
  AppShell
    SidebarLayer
    MainColumn
      TopBarLayer
      MainScrollArea
    OverlayRoot
    GlobalAssistLayer
```

重点是：

- 侧边栏不再由页面自己拼
- 主内容滚动区唯一
- overlay 不再依赖页面内部层级
- toast、看板娘、全局辅助层归一

## 6. 关键模块的改造策略

这一部分不是列名单，而是说明每类模块怎么改。

## 6.1 搜索链路

核心对象：

- [`SearchPage`](../../src/pages/SearchPage/index.tsx:40)
- [`TopBar`](../../src/components/layout/TopBar.tsx:36)
- [`searchApi`](../../src/features/search/api/searchApi.ts:32)
- [`useSearchStore`](../../src/features/search/store/searchStore.ts:65)

### 目标状态

- 搜索条件进入 URL
- 搜索页只做编排
- 搜索参数解析独立
- query hook 负责取数
- store 不再承担完整查询条件

### 实施重点

1. 先定义统一的搜索 URL 参数协议
   - `q`
   - `channel`
   - `include_tags`
   - `exclude_tags`
   - `sort`
   - `page`
   - `time_from`
   - `time_to`

2. 把“解析 URL 到请求参数”的逻辑从页面里抽走
3. 把“页面局部输入态”和“实际查询态”区分清楚
4. 把 preview、banner、filters 从巨石组件中逐步拆分

### 风险

- 浏览器前进后退行为可能和当前不一致
- 搜索历史、token 输入、标签点击注入需要重新梳理
- 无限滚动和 URL 分页如何共存要先定规则

### 验收标准

- 刷新不丢筛选
- 链接可分享
- 页面不再依赖巨型 search store 完成主链路

---

## 6.2 布局链路

核心对象：

- [`RootLayout`](../../src/components/layout/RootLayout.tsx:5)
- [`MainLayout`](../../src/components/layout/MainLayout.tsx:14)
- [`AppSidebar`](../../src/components/layout/AppSidebar.tsx:14)
- [`ResizableSidebar`](../../src/components/ResizableSidebar.tsx:1)

### 目标状态

- 应用壳层真正统一
- 页面不再复制布局
- Sidebar、TopBar、MainScrollArea 责任清楚

### 实施重点

1. 先定义 App Shell 的标准树
2. 把布局职责从页面中回收到壳层
3. 重新划分 Sidebar、TopBar、Notification 面板的层级
4. 明确移动端打开关闭逻辑和滚动锁定

### 风险

- 搜索页现有体验最容易被影响
- 移动端和桌面端行为可能出现分叉
- ResizableSidebar 的保留范围要提前定

### 验收标准

- 搜索页不再自己拼一套主布局
- 全站主滚动区唯一
- 浮层不会被父容器裁剪

---

## 6.3 认证链路

核心对象：

- [`App`](../../src/app/App.tsx:34)
- [`ProtectedRoute`](../../src/components/ProtectedRoute.tsx:6)
- [`authApi`](../../src/features/auth/api/authApi.ts:17)

### 目标状态

- token 提取入口统一
- route guard 只负责路由守卫
- 登录回跳逻辑可读可测

### 实施重点

1. 收口 token hash 回收逻辑
2. 去掉 [`App`](../../src/app/App.tsx:35) 和 [`ProtectedRoute`](../../src/components/ProtectedRoute.tsx:14) 的重复职责
3. 把认证 query 与路由守卫解耦

### 风险

- OAuth 回跳最容易出问题
- 需要谨慎处理老链接和 sessionStorage 回跳逻辑

### 验收标准

- 认证流程只有一个 token 回收入口
- 未登录跳转逻辑稳定
- 登录回跳路径正确

---

## 6.4 设置链路

核心对象：

- [`useSettings`](../../src/hooks/useSettings.ts:4)
- [`lib/settings.ts`](../../src/lib/settings.ts:3)

### 目标状态

- 保留当前轻量配置体验
- 补 schema 校验和版本迁移
- 设置模块不再只是 localStorage 拼接器

### 实施重点

1. 给设置结构加 schema
2. 设置恢复时做校验和回退
3. 视情况逐步拆分主题、布局、通知、实验项

### 风险

- 老用户本地设置兼容
- 主题字段历史兼容要保留

### 验收标准

- 脏数据不会导致页面异常
- 设置项可以稳定扩展

---

## 6.5 通知与预览链路

核心对象：

- [`NotificationCenter`](../../src/features/notifications/components/NotificationCenter.tsx:27)
- [`GlobalThreadPreview`](../../src/app/App.tsx:64)
- [`FloatingBanner`](../../src/app/App.tsx:63)

### 目标状态

- 通知、预览、banner 不再各自占一套隐式规则
- 统一归入全局交互层和 overlay 体系

### 实施重点

1. 区分数据组装层和面板展示层
2. 把 preview 状态从搜索语义里拆出来
3. 明确 banner 是页面态、全局态，还是混合态

### 验收标准

- 通知、预览、banner 的触发和展示边界清楚
- 不再通过页面内部副作用“顺带驱动”全局能力

## 阶段 1：应用骨架收口 [x]

### 目标

先把全站骨架统一，避免页面一边拆业务一边继续复制布局。

### 动作

1. 收敛 `RootLayout`、`MainLayout`、全局挂载层职责
2. 确定 App Shell 的标准结构
3. 明确 Sidebar、TopBar、MainScrollArea 的挂载关系
4. 预留统一 overlay root

### 输出

- 页面以后只插内容，不自己搭骨架
- 全站层级和滚动规则统一

### 依赖

- 依赖布局文档和目录建议

### 风险

- 搜索页改动会最敏感
- 需要控制“结构变更但 UI 尽量不抖”的节奏

### 阶段验收

- 搜索页不再复制主布局
- 主滚动容器唯一
- overlay 挂载点明确

---

## 阶段 2：搜索链路重构

### 目标

把最核心业务从“巨石页面 + 巨型 store”变成“URL + query + feature 编排”。

### 动作

1. 设计统一搜索参数协议
2. 抽参数解析与序列化层
3. 将查询条件迁移到 URL
4. 拆出搜索页 section 或 widgets
5. 收缩 [`useSearchStore`](../../src/features/search/store/searchStore.ts:65)

### 输出

- 搜索链路单向化
- 搜索页面明显变薄
- 搜索 URL 真正可分享

### 风险

- 无限滚动与分页的体验折中
- 标签注入和高级搜索联动逻辑容易出错
- 历史搜索行为要重新对齐

### 阶段验收

- 搜索条件刷新不丢失
- 页面逻辑明显减少
- 结果请求和 UI 组合逻辑解耦

---

## 阶段 3：全局交互层收口

### 目标

把通知、预览、banner、看板娘等全局交互收回统一规则。

### 动作

1. 统一 preview flow
2. 调整 notification panel 的挂载和状态归属
3. 重新定义 page banner 和 global banner 的边界
4. 给全局交互能力建立固定落点

### 输出

- 全局交互层不再散装
- 页面不再背负过多全局副作用

### 风险

- 看板娘和错误反馈联动逻辑可能出现回归
- 通知未读数与关闭行为需要谨慎验证

### 阶段验收

- 预览、通知、banner 边界清楚
- 主要浮层层级稳定

---

## 阶段 4：设置、安全、稳定性补强

### 目标

把当前“能跑”的基础能力补到“可长期维护”的水平。

### 动作

1. 设置 schema 与版本迁移
2. Markdown 安全规则落地
3. 外链统一处理
4. token 处理入口统一
5. 错误边界和基础日志能力补强

### 输出

- 设置恢复更稳
- 富文本链路更安全
- 认证副作用更可控

### 风险

- 老数据兼容
- Markdown 展示可能因为白名单收紧而发生变化

### 阶段验收

- 设置脏数据不致命
- 无裸 HTML 注入链路
- 认证异常有稳定回退

---

## 阶段 5：测试和体验收口

### 目标

让重构不是一次性运动，而是能继续演进。

### 动作

1. 补高收益工具测试
2. 补关键页面链路测试
3. 统一空、错、加载、成功四态
4. 收敛体验文档里的 P0 内容

### 输出

- 核心重构链路有安全网
- 体验规范可以复用

### 风险

- 如果前面阶段没控制边界，这里会变成补锅

### 阶段验收

- 至少有基础测试门禁
- 关键页面四态统一
- 文档和代码状态一致

## 8. 目录升级如何嵌入实施计划

目录升级不应单独变成一场大迁移，而应嵌入各阶段中完成。

### 原则

- 不先做全量重命名
- 谁被重构，谁顺手迁目录
- 新代码优先落到目标目录结构

### 推荐嵌入点

- 阶段 1：把布局层逐步收进 `app/layout`
- 阶段 2：拆搜索页时建立 `pages/search`、`features/search/model`、`widgets/top-bar`
- 阶段 3：把通知和预览面板逐步迁到 `widgets`
- 阶段 4：把通用工具逐步收口到 `shared`

目录建议详见 [`目录架构升级建议.md`](./目录架构升级建议.md)。

## 9. 本轮明确延期的内容

为了防止范围失控，这些内容可以记入后续路线，但不纳入本轮硬交付：

- 真正的推荐流
- 命令面板
- OpenAPI 自动生成
- 高级图片占位技术
- 大规模视觉焕新
- 复杂数据埋点体系

不是这些不重要，而是它们一旦和主重构绑定，会显著拖慢主线。

## 10. 风险矩阵

## 高风险

### 搜索 URL 化

原因：

- 牵扯输入、筛选、分页、历史记录、无限滚动

控制方式：

- 先定义参数协议
- 先跑通最小链路
- 再补高级筛选和联动

### OAuth 回跳链路

原因：

- 当前 [`App`](../../src/app/App.tsx:35) 和 [`ProtectedRoute`](../../src/components/ProtectedRoute.tsx:14) 都碰 token

控制方式：

- 统一 token 回收入口
- 先补测试再调整

## 中风险

### 布局骨架统一

原因：

- 搜索页高度依赖当前自建布局

控制方式：

- 先保持 UI 外观接近
- 优先做结构回收，不同时做视觉重做

### 通知与预览收口

原因：

- 当前属于“能用但散装”的状态

控制方式：

- 先分状态边界，再改 UI 挂载

## 低风险

### 设置 schema 化

原因：

- 相对独立，可单点推进

控制方式：

- 保留默认值和旧字段兼容

## 11. 验收标准

验收不能只写抽象词，这里按层给出标准。

## 11.1 架构验收

满足以下条件，说明架构重构基本成立：

- 页面组件明显变薄
- 搜索主链路不再依赖巨型全局 store
- 应用骨架统一
- 目录职责比当前更清楚

## 11.2 工程验收

- 后续新功能知道应该放哪一层
- 状态边界在文档和代码中一致
- 目录升级不是一次性硬迁，而是有顺序地收口
- 关键链路有最小测试保护

## 11.3 体验验收

- 搜索刷新不丢条件
- 浏览器前进后退可恢复状态
- 浮层层级稳定
- 空、错、加载、成功四态统一
- 移动端基础交互不崩

## 11.4 文档验收

- 文档之间不再互相打架
- 每篇文档有清楚分工
- 开发实现时可以直接拿文档拆任务

## 12. 推荐实施顺序总结

如果后续要真正开始改代码，建议按下面顺序进入：

1. 先按 [`现状问题清单与代码映射.md`](./现状问题清单与代码映射.md) 锁定首批改造对象
2. 按 [`UI层级和父子容器优化.md`](./UI层级和父子容器优化.md) 收口应用骨架
3. 按 [`状态管理与数据流重构.md`](./状态管理与数据流重构.md) 重构搜索主链路
4. 结合 [`目录架构升级建议.md`](./目录架构升级建议.md) 做渐进迁目录
5. 再补 [`安全升级.md`](./安全升级.md) 和 [`测试升级.md`](./测试升级.md) 里的收尾项
6. 最后根据 [`细节打磨.md`](./细节打磨.md) 收 P0 体验项

这套顺序的核心原则只有一句：

**先收骨架，再拆主链路，最后补稳定性和体验。**
